# Deployment — Rohani Shifa

How this Angular 22 SPA gets to production: static hosting on GitHub Pages, data plane on
Firebase (Auth + Firestore). There is no server to host — everything the browser runs is
static files; all writes go directly to Firebase from the client and are gated by
`firestore.rules`.

Firebase *project* setup (creating the project, enabling providers, granting admin claims)
is out of scope here — see `FIREBASE_SETUP.md`.

Commands below are written for Windows PowerShell. On Windows, call npm as `npm.cmd`
(plain `npm` can be blocked by the execution policy), and check `$LASTEXITCODE` after
redirecting output, because redirected builds can otherwise hide a failing exit code.

## 1. Overview

| Piece | Where it runs | How it gets there |
|---|---|---|
| Static SPA (HTML/JS/CSS, hashed assets) | GitHub Pages, `gh-pages` branch, sub-path `/RohaniShifaPostApp/` | `npm.cmd run deploy` → `ng deploy` → `angular-cli-ghpages:deploy` builder |
| Auth + Firestore data | Firebase project (client SDK, no backend code) | Config baked into `src/environments/environment.prod.ts` at build time |
| Firestore rules + composite indexes | Firebase project | `npx firebase-tools deploy --only firestore:rules,firestore:indexes --project <id>` |
| SPA fallback (`404.html`) and `.nojekyll` | `gh-pages` branch | Auto-generated by the `angular-cli-ghpages` builder on every deploy |

Nothing else needs hosting: no Cloud Functions exist in this project (engagement counters
are maintained by client transactions), and `firebase.json` wires only the `firestore`
key.

## 2. Prerequisites

- Node.js + npm (`packageManager: npm@11.19.1` in `package.json`); `node_modules`
  installed via `npm.cmd install`.
- Git 1.9+ with working push credentials for the GitHub repo. The builder pushes the
  `gh-pages` branch to the `origin` remote (configurable via `repo` / `remote`).
  For HTTPS remotes, a `GH_TOKEN` / `GITHUB_TOKEN` / `PERSONAL_TOKEN` environment
  variable is used automatically; SSH remotes need a working SSH key (tokens are not
  supported over SSH).
- A GitHub repository the account can push to.
- A Firebase project with a **Web app** registered (source of the web config values).
  See `FIREBASE_SETUP.md`.
- A git identity on the machine (`git config user.name` / `user.email`), or pass
  `--name` / `--email` to `ng deploy` — the builder must create a commit.
- Note: the local repo currently has **no remote** and one scaffold commit
  (`master`, `a663836 initial commit`) with the application code still uncommitted.
  Add the remote and commit before deploying (steps below).

## 3. One-time configuration checklist

Every value that must be filled in before a real (non-demo) deployment:

| File / setting | Field | Where the value comes from | If left as placeholder |
|---|---|---|---|
| `src/environments/environment.prod.ts` | `firebase.apiKey` | Firebase console → Project settings → Your apps → SDK config | Demo mode |
| `src/environments/environment.prod.ts` | `firebase.authDomain` | Same SDK config (`<project>.firebaseapp.com`) | Sign-in fails / misconfigured auth |
| `src/environments/environment.prod.ts` | `firebase.projectId` | Same SDK config | Demo mode |
| `src/environments/environment.prod.ts` | `firebase.storageBucket` | Same SDK config (note: current default is `<project>.firebasestorage.app`) | Storage unavailable (unused today) |
| `src/environments/environment.prod.ts` | `firebase.messagingSenderId` | Same SDK config | Messaging unavailable (unused today) |
| `src/environments/environment.prod.ts` | `firebase.appId` | Same SDK config | Demo mode |
| `src/environments/environment.prod.ts` | `firebase.measurementId` | Same SDK config (only if Analytics enabled) | Analytics unavailable; `analyticsEnabled` is `false` anyway |
| `src/environments/environment.prod.ts` | `baseHref` | `'/<repo-name>/'` — must **equal** the `baseHref` of the deploy target in `angular.json` (`/RohaniShifaPostApp/`) | Canonical/OG URLs in `SeoService` point at the wrong path |
| `angular.json` → `architect.deploy.options` | `baseHref` | `'/<repo-name>/'`; already `/RohaniShifaPostApp/` | Built assets resolve against the wrong root → blank page |
| Firebase console → Auth → Settings → **Authorized domains** | list entry | Add `<user>.github.io` (and `localhost` for dev) | Firebase Auth sign-in/popup errors from the Pages origin |
| `src/environments/environment.ts` (dev) | `firebase.*` | Dev web app config (optional) | Dev also runs in demo mode — fine for pure UI work |

Demo-mode detection is precise: `isFirebaseConfigured()` in
`src/app/core/firebase/firebase.service.ts` checks that `apiKey`, `projectId` and `appId`
do not start with `REPLACE_WITH`. Until all three are replaced, `FirebaseService.configured`
stays `false`: the Firebase SDK is never initialized, all data services return empty
observables, public pages render empty states / the demo-mode notice, the auth pages show
the configuration notice instead of signing in, and `/admin/*` redirects to `/login`
(because nobody can be logged in). This is safe to deploy intentionally, e.g. for a UI
preview.

## 4. Local verification before deploying

Run from the repo root in PowerShell:

```powershell
# Build (production config; also performs the environment.prod.ts file replacement)
npm.cmd run build > $env:TEMP\build-out.txt 2>&1; $code=$LASTEXITCODE; Get-Content $env:TEMP\build-out.txt; if ($code -ne 0) { throw "build failed: $code" }

# Unit tests (vitest via the @angular/build:unit-test builder)
npm.cmd test > $env:TEMP\test-out.txt 2>&1; $code=$LASTEXITCODE; Get-Content $env:TEMP\test-out.txt; if ($code -ne 0) { throw "test failed: $code" }

# Dev server — http://localhost:4200/
npm.cmd start
```

Why the redirection trick: on this Windows setup a piped/redirected npm build can report
success incorrectly; writing output to a file and checking `$LASTEXITCODE` is the only
trustworthy signal.

## 5. Deploying to GitHub Pages

1. Create the (empty) GitHub repository, then attach it as the remote and push the source:

   ```powershell
   git remote add origin https://github.com/<user>/RohaniShifaPostApp.git
   git push -u origin master
   ```

   Current state: no remote is configured yet; add it before deploying.

2. Deploy:

   ```powershell
   npm.cmd run deploy
   ```

   This runs `ng deploy`, which invokes the `deploy` target in `angular.json`
   (`angular-cli-ghpages:deploy` builder) with the committed options:
   `buildTarget: rohani-shifa:build:production`, `baseHref: /RohaniShifaPostApp/`,
   `branch: gh-pages`, `message: "deploy: publish GitHub Pages build"`.
   Override anything on the command line, e.g.
   `npm.cmd run deploy -- --name="Your Name" --email=you@example.com` for the commit
   identity.

3. What the builder does, in order:
   - Runs the production build: `rohani-shifa:build:production` — which swaps
     `src/environments/environment.ts` for `environment.prod.ts` via `fileReplacements`,
     applies output hashing and budgets, and rewrites the `<base href>` in the built
     `index.html` to `/RohaniShifaPostApp/`.
   - Publishes the build output (default for this project:
     `dist/rohani-shifa/browser`) onto the `gh-pages` branch of the `origin` remote
     (a fresh orphan-style publish; the branch is force-pushed, old files are replaced).
   - Generates `404.html` (copy of `index.html` — SPA fallback, see section 6) and
     `.nojekyll` (prevents GitHub's Jekyll pipeline from processing the files).
   - Useful builder options (from `node_modules/angular-cli-ghpages/deploy/schema.json`):
     `dryRun` (rehearse without pushing), `cname` (custom domain, section 9), `repo` /
     `remote` (target repo/remote instead of `origin`), `dir` (publish a different
     directory), `add` (append to the branch instead of replacing), `noBuild` (reuse the
     last build output), `noNotfound` / `noNojekyll` (skip the generated files — do not
     use on GitHub Pages).

4. In the GitHub repo: **Settings → Pages → Build and deployment → Source: Deploy from a
   branch → Branch: `gh-pages` / `(root)`**. First-time activation only.

5. Site URL: `https://<user>.github.io/RohaniShifaPostApp/`
   (formula: `https://<user>.github.io/<repo-name>/`). Pages builds take a minute or two
   on first publish.

If placeholders are still in place, the deployed site runs in demo mode (empty states,
auth disabled) — that is expected behaviour, not a failure.

## 6. SPA routing on GitHub Pages

- The router is path-based, so a hard reload or direct link on
  `https://<user>.github.io/RohaniShifaPostApp/admin` must serve the SPA shell. GitHub
  Pages has no server-side rewrite rules; the builder's generated `404.html` (a copy of
  the app's `index.html`) is the standard workaround — GitHub serves it for unknown
  paths and the Angular router takes over once loaded.
- Caveat, accepted for this app: GitHub still returns **HTTP 404** for those deep links.
  Link previews / crawlers that do not execute JavaScript see a 404 status. JS-executing
  crawlers and human navigation are unaffected.
- `baseHref` must match the repo sub-path exactly (`/RohaniShifaPostApp/`). If the repo
  is renamed or forked under a different name, update both the deploy target's `baseHref`
  in `angular.json` **and** `environment.prod.ts → baseHref`, then redeploy — otherwise
  the page loads with no styling/scripts (assets requested from the wrong root).
- `/admin` is declared before the SPA fallback route in `src/app/app.routes.ts`, so it
  never collides with the client-side 404 page.

## 7. Post-deploy Firebase steps

1. Deploy Firestore rules and composite indexes (both files are wired in `firebase.json`
   under the `firestore` key only; `firebase-tools` is not a dependency — `npx` fetches
   it on demand):

   ```bash
   npx firebase-tools deploy --only firestore:rules,firestore:indexes --project <project-id>
   ```

   Rules (`firestore.rules`) are the real security boundary — route guards are UX only.
   `firestore.indexes.json` defines the composite indexes the content/feed queries need.

2. Firebase console → Auth → Settings → **Authorized domains**: add `<user>.github.io`.
   Without it, sign-in fails on the Pages origin while working on localhost. (`localhost`
   is already in the default list.)

3. Firestore has no CORS/authorized-domain concept — access is governed purely by the
   security rules deployed in step 1, so no domain registration is needed for reads and
   writes from the browser. If you later enable **App Check** (not configured in this
   project), register the Pages domain there as well.

4. Granting the first admin account (custom claim) happens outside the app — see
   `FIREBASE_SETUP.md`.

## 8. Re-deploys and rollbacks

- Re-deploying is just re-running `npm.cmd run deploy`. The builder force-pushes the
  `gh-pages` branch: it is rebuilt from scratch each time, so stale hashed assets do not
  accumulate (note the `add` option, if ever set, would change this).
- The `gh-pages` branch is generated output — never edit it by hand.
- **Rollback**: check out the last good commit of `master`, verify locally, and run
  `npm.cmd run deploy` again. Because output hashing changes per build, an incremental
  "revert one file" approach does not work; the whole site is republished.
- Data (Firestore) is not rolled back by any of this — rules/indexes deploys are
  independent of the Pages deploy.

## 9. Optional additions (not currently configured)

### Custom domain

1. `angular-cli-ghpages` writes a `CNAME` file into the published branch:

   ```powershell
   npm.cmd run deploy -- --cname=www.example.com
   ```

2. Point DNS at GitHub (CNAME record for `www`, or A records for the apex — see GitHub's
   docs), then enable HTTPS in **Settings → Pages**.
3. Update **both** `baseHref` values to `'/'` (root hosting): the deploy target in
   `angular.json` and `environment.prod.ts → baseHref`. Set
   `environment.prod.ts → firebase.authDomain` to the custom domain, and add that domain
   to Firebase Auth → Authorized domains.

### CI deployment (GitHub Actions) — not configured

There is no `.github/workflows/` in this repo; deploys are manual from a workstation.
If CI is wanted, a minimal workflow using the same builder (label this experimental
until adopted):

```yaml
# .github/workflows/deploy-pages.yml  (OPTIONAL — does not exist yet)
name: Deploy to GitHub Pages
on:
  push:
    branches: [master]
permissions:
  contents: write
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22, cache: npm }
      - run: npm ci
      - run: npx ng deploy
        env:
          # GH_TOKEN = classic PAT with repo scope, stored as a repo secret.
          # In PUBLIC repos the built-in GITHUB_TOKEN does NOT trigger a Pages
          # rebuild — a PAT (GH_TOKEN) is required. Tokens only work over HTTPS.
          GH_TOKEN: ${{ secrets.GH_TOKEN }}
```

(`ng deploy` reads the deploy options — `buildTarget`, `baseHref`, `branch`, `message` —
from `angular.json`, so no extra flags are needed.)

## 10. Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| Blank page; browser console shows assets 404 under `/RohaniShifaPostApp/…` (or assets requested from `/`) | `<base href>` mismatch — repo renamed, or the two `baseHref` values (angular.json deploy target vs `environment.prod.ts`) disagree | Make both `'/<repo-name>/'`, redeploy, hard-refresh |
| Deep link / reload returns GitHub's 404 page (app shell missing) | `404.html` not published (`noNotfound` set) or Pages source is not the `gh-pages` branch | Redeploy with defaults; check Settings → Pages → Source = `gh-pages` / `(root)` |
| Site not live an hour after a successful deploy | Pages not enabled, or deploy pushed to a repo other than the one Pages serves | Check Settings → Pages; check `git remote -v` and the `repo`/`remote` deploy options |
| `/admin` redirects to `/login` on the deployed site | Demo mode (placeholders still in `environment.prod.ts`) — nobody can sign in; or the account lacks the `admin` custom claim | Replace placeholders and redeploy; grant the claim per `FIREBASE_SETUP.md` |
| Sign-in fails on Pages but works on localhost | `<user>.github.io` missing from Firebase Auth → Authorized domains | Add the domain in the Firebase console |
| Firestore reads/writes throw `permission-denied` | Rules not deployed to the project, or rules reject the operation | Run the rules/indexes deploy command (section 7) |
| Firestore error: "The query requires an index" | Query needs a composite index missing from `firestore.indexes.json` | Add the index definition, redeploy indexes |
| `ng deploy` fails: repository not found / auth error | No `origin` remote yet, or push credentials missing | `git remote add origin …`; use HTTPS + credential manager/SSH key, or a `GH_TOKEN` env var with an HTTPS remote |
| `ng deploy` fails creating the commit | No `user.name`/`user.email` git identity | Set them globally, or pass `--name` / `--email` |
| Files missing from the published site | Dotfile filtering (`noDotfiles`) | Leave the default (dotfiles included — `.nojekyll` must ship) |
